# Phase M6C Checkpoint 3 — Shared provider contract adoption

Baseline: M6C Checkpoint 2 was review-corrected by PR #77 at application commit `6e5728a5061d0d9d6e5f21cd117086e6a4dca572`.

## Objective

Apply the provider registry and normalized capability contract to the shared movie-aggregate and comparison presentation boundaries without adding a real fourth cinema chain or rewriting current provider adapters.

## Shared provider core

`app/provider-shared-core.js` is the neutral bridge between `provider-registry.js`, `provider-contract.js` and shared presentation/runtime code.

It owns:

- registry enumeration as `{ key, label, descriptor }` records;
- provider-ID lists and provider-keyed state-map construction;
- registry-driven display labels;
- normalized aggregate source-ID lookup;
- active-provider enumeration for a movie aggregate;
- optional price / seat-summary / booking capability evaluation;
- provider-count labels that preserve the accepted `兩院線` / `三院線` wording and scale to `4 院線`, etc.

The production page loads the contract and shared core immediately after the registry and before home/comparison modules.

## Home/movie aggregation adoption

`phase8a-movie-navigation.js` no longer owns a fixed Broadway/MCL/Emperor provider list. It obtains provider IDs from the shared registry core.

A movie card can expose a provider-scoped source through the neutral pair:

- `data-provider="<provider-id>"`
- `data-source-id="<provider-source-id>"`

It can also expose a provider-keyed JSON map through `data-provider-sources` where a card already represents multiple sources. Existing Broadway/MCL/Emperor data attributes/classes remain supported for compatibility.

Aggregate `sources`, `providerCount`, match entries and variant source maps are generated by registry enumeration. The fourth-provider fixture test proves that a card with `data-provider="fixture"` becomes a valid aggregate and match record without adding a `provider === "fixture"` branch.

Provider catalogue lookup remains adapter-aware. Current Broadway/MCL/Emperor catalogue globals are different upstream interfaces; retaining those lookups is legitimate adapter knowledge, not shared capability presentation logic.

## Comparison adoption

`provider-compare-v4.js` now obtains provider descriptors from the shared core and creates `availableDates`, criteria-decision, data, error and freshness maps dynamically.

Shared comparison behavior now includes:

- aggregate provider enumeration from provider-keyed `sources`;
- registry-driven provider labels;
- dynamic provider-count date labels;
- dynamic `getState().availableDates` / source-ID maps;
- a generic normalized-showtime path for a provider that is not Broadway, MCL or Emperor;
- descriptor-driven price, seat-summary and booking presentation semantics.

Each rendered showtime card records:

- `data-price-capability`;
- `data-seat-capability`;
- `data-booking-capability`.

For a provider that explicitly declares `prices: false`, the price area shows `不提供` rather than `HK$0` or a fabricated value. For `seatSummary: false`, the seat line shows `座位資料不提供` rather than sold-out/no-seat wording. A supported capability with missing data retains the existing unknown presentation. A valid booking link remains usable independently from price/seat support.

## Provider-specific adapters intentionally retained

Checkpoint 3 does **not** remove branches that correspond to real upstream differences:

- MCL comparison fetch continues to use the MCL ticketing adapter.
- Broadway and Emperor current comparison requests continue through the Worker route.
- Broadway, MCL and Emperor session normalizers remain because their seat/price payloads differ.
- MCL generic-bridge/session-criteria behavior remains MCL-specific.
- `multi-provider.js` continues to merge the currently integrated MCL/Emperor catalogues into the Broadway-origin home grid; that is current provider-integration orchestration, not the normalized presentation contract.
- MCL lazy price enrichment remains an MCL-specific adapter.

A future provider can enter the shared aggregate/comparison boundary after its provider adapter supplies normalized catalogue/showtime data; Checkpoint 3 does not pretend all upstream APIs are interchangeable.

## Fourth-provider expansion proof

`tests/m6c-shared-provider-adoption.test.mjs` extends the registry in-memory with the existing `fixture` descriptor and proves:

1. provider enumeration and state maps contain four providers;
2. the fixture aggregate is recognized through provider-keyed `sources`;
3. a fixture movie card becomes a valid Phase 8A aggregate/match record without provider-name branching;
4. a fixture showtime remains valid when price and seat capabilities are unsupported;
5. booking stays available independently;
6. current supported-but-missing capabilities remain `unknown`;
7. production load order installs registry → contract → shared core before shared home/comparison code.

No real fourth provider, endpoint or parser is introduced.

## Non-goals

This checkpoint does not:

- add or fetch a real fourth cinema chain;
- rewrite Broadway/MCL/Emperor parsers;
- generalize provider-specific seat-map request/layout code;
- change accepted Metro or Classic visual structure;
- alter the Service Worker live-data/cache boundary;
- change MCL lazy price request concurrency.

Those request/failure-isolation topics belong to M6D.
